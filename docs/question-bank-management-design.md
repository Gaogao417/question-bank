# 题库录入与管理：AI、程序与 Review UI 的接口设计

更新：2026-09-27。状态：目标设计，尚未实施。

## 1. 用户要求与设计中心

用户明确：人通过 Review UI 修订和调整产物，尤其帮助 AI 处理图片等难以自行调好的内容；AI 提供能通过程序校验的产物，程序接收并交给 Review UI 呈现；人的修改通过 Review UI 写入数据库。

因此，系统围绕以下闭环设计：

```text
原始试卷与参考答案
       ↓
AI 产出结构化候选 ──校验失败及定位反馈──→ AI 修正
       ↓ 程序校验并接收
数据库中的待审题目与明确疑点
       ↓ 查询                         ↑ 保存新修订
Review UI ←──────── 人查看、修订文字、调整图片、处理疑点
       ↓ 人确认当前版本
数据库中的复核与发布状态 → 题库使用及兼容导出
```

人不需要改 YAML、拼文件路径或通过聊天指挥脚本来完成日常修订。AI 不直接操作数据库，不直接修改已被人工修订的正式内容。程序提供统一的接收、读取、编辑、复核和发布能力，Review UI 与 AI 入口调用同一套业务规则。

本设计取代本次初稿中的“文件唯一真源、SQLite 仅派生索引”方向。**目标是数据库管理题目当前内容、修订、人工修改和审核发布事实；文件保留原始材料、媒体与可追溯的输入输出。** 不建立文件与数据库双向覆盖的两套真源。

后续题库录入与管理改造以本文为目标依据；旧架构文档仅在不冲突的范围内解释已有实现。本仓负责誊录与内容资产，不复制课堂运行时；跨仓合同仍从 `ai_teaching_prds_v2_00-07/contracts/` 修改。本文内部接口草案不自动成为跨仓合同。

## 3. 三个接口与职责

| 接口 | 输入/操作 | 返回及责任边界 |
|---|---|---|
| AI ↔ 程序 | 提交候选内容、来源证据、媒体引用与待人工处理项 | 程序验证、规范化、持久化；返回接收回执或结构化错误。AI 不伪造批准、不直写业务表 |
| 人 ↔ 程序 | Review UI 中查看原页和候选、编辑文字、裁图/换图/调归属、保存、复核 | 后端校验编辑并提交数据库；UI 展示真实保存结果和当前版本，不依赖手工文件同步 |
| 人 ↔ AI | 人通过 UI 的疑点或修订要求指定某题某字段需要 AI 帮助 | 程序组织带当前版本的局部任务；AI 返回修改建议；UI 比较并由人接受或继续编辑，不让 agent 整题重写覆盖人工成果 |

AI 的交付目标是“程序可接收、UI 可展示并继续编辑”，不要求在进入 UI 前解决所有视觉或内容疑点。程序校验通过只说明符合接收契约，不等于数学内容正确或已经批准。

图片缺失、归属不明、原答案疑似印错可以作为合法的待审状态进入 UI。结构必须完整表达未知状态及证据，不能以伪造答案或图片通过校验；此类问题阻止批准/发布，不阻止人看见并修复。

## 4. AI 提交契约与接收回执

先复用现有 draft/transcription 契约及展开器，通过一个薄适配层形成统一题目编辑模型；不用让 AI 直接编写 teacher/student 两套消费文件或 UI 组件路径。现有 assignment_path 等路径规则逐步由适配层承担，过渡期仍验证旧产物。

候选包至少包含：

- 来源身份：paper_id、原题号、来源文件/页码/原文定位；试卷预期题号单独确认，不默认每卷 25 题。
- 内容：三块正文（题目、答案、解答）+ 少量结构化字段，见 §9；不再强制 choices[]、subquestions[]、solution_steps[] 等深结构，小问、选项与推导顺序在正文文本中表达。原卷誊录与 AI 建议/生成的提示分开。
- 媒体：稳定 asset_id 或受控导入引用、题干/答案角色、必要的源页与裁框；坐标以明确的原图像素坐标系保存。
- 疑点：稳定 issue_id、类型、影响字段/图片、原因、来源证据和建议处理方式。
- 提交信息：submission_id、目标题目身份、输入来源 hash；修改已有题时必须带 base_revision。

程序负责文件引用可访问性、媒体字节/尺寸、类型与字段、跨字段一致性、身份唯一性、证据关联和安全路径校验。不得让 AI 猜数据库主键或写任意磁盘路径。

错误反馈包含 code、item_key、field_path、message、fix_hint 及 retryable；按题定位，不把一题失败变成全卷重做。合法候选可接收为 accepted_with_issues；硬结构错误 rejected；过期版本 conflict；完全相同的提交 noop。

成功回执返回 submission_id、item_id、revision、content_hash、接收状态和 Review UI 可定位链接/标识。传输中断后用 submission_id 查询回执；相同 submission_id 不同载荷拒绝，禁止重复插入或猜测成功。

CLI/脚本只是该接口的客户端。固定的扫描聚合、任务生成、校验和接收由程序执行，AI 专注转写与语义判断。模型调用设置明确预算、并发和修复次数；保留每次失败，不无条件重跑、不跨供应商回退。

## 5. Review UI 的编辑闭环

沿用现有页面交互结构，优先把已有图片与审核能力接通数据库，再补齐必要的正文编辑与局部 AI 修订入口，不无故重排前端。

### 5.1 展示与编辑

后端提供一个题目编辑视图：数据库当前修订、原始页图/媒体、疑点、已有人工修改、复核状态及已发布版本。题干与解答使用同一规范内容模型（§9 三块正文）渲染；不得展示旧导出文件而编辑另一份内容。

人可以修改题目、答案、解答三块正文；裁切、替换、删除或调整图片角色/顺序；解决或备注疑点。保留原始图与原始誊录供比较，人工修订不冒充原卷原文。

图片操作保存为明确数据：原图 asset_id、裁框、旋转等变换及归属；粘贴/上传的新图先成为不可变媒体资产，再绑定题目。图片预览由同一变换生成，避免 UI 看见一个裁框、导出使用另一个裁框。AI 无法调好的图片交给人调整，不为了通过机器规则反复强迫 AI 猜图。

### 5.2 保存

UI 提交 item_id、base_revision、编辑 patch、operation_id。程序再次校验并在数据库事务内创建新修订，更新当前修订指针及变更记录；返回保存后的规范内容、revision 和 hash。UI 用回执刷新，保存成功后刷新页面、重启服务仍一致。

人可先保存带未解决内容疑点的草稿；无效结构或越界裁框返回字段错误，保留浏览器编辑内容，不假装已保存。保存与批准分开；内容或媒体修改会使旧批准不适用于新版本。

两个人或 AI 同时改动时使用 base_revision 乐观并发校验。版本冲突返回冲突字段与新版本，UI 保留未保存修改并提供比较；禁止静默最后写入覆盖。

### 5.3 人要求 AI 再修订

任务包含当前修订和指定范围。AI 建议独立保存，与当前内容做差异比较；默认不自动覆盖人工修改。即使基线尚未变化，已有人工修订题上的 AI 改动也先作为建议，用户通过 UI 接受后才形成新当前修订。基线变化时必须重新比较，不能套用旧整题输出。

无需每次让人审批普通首次 AI 录入；首次候选可直接接收为待审。人工介入集中在 Review UI 内容调整、疑点处置与现有发布政策要求的确认。

## 6. 数据库、媒体与产物的归属

采用本地 SQLite 即可，不为题库另建分布式数据库或通用事件平台。最小逻辑实体：

| 实体 | 权威内容 |
|---|---|
| papers / paper_items | 试卷元信息、预期题目集合、题序与来源关联 |
| items / revisions | 稳定身份、当前修订、不可变的规范题目内容及 hash |
| assets / revision_assets | 媒体 hash、受管理位置、来源及各修订的引用/变换 |
| issues / checks / reviews | 疑点及处理、结构检查、模型复核或人工批准，均绑定修订 |
| submissions / operations | AI 接收与 UI 保存的幂等回执、操作者类型及变更记录 |
| publications | 发布修订指针、撤回及历史 |
| runs / proposals | 模型任务、输入基线、输出、失败和待接受的修改建议 |

具体表可合并，先满足闭环，不为名称建空框架。业务元数据与事务事实入数据库；原始来源、大媒体、原始模型响应存受管理文件并以 hash 引用。

YAML/JSON 是导入包、历史证据或数据库导出产物。接收成功后，不再监听旧 draft 自动覆盖数据库，也不将 UI 修改重新塞回 AI 原始输出以伪造“原始候选”。teacher/student assignment、question-bank.yaml 供旧消费者使用，迁移完成后由指定数据库修订生成。

**数据库不是可删除重建的缓存。** 必须备份业务数据库与其引用的媒体，验证恢复后的修订、人工修改、审核及发布一致。可重建的只是查询索引、预览和兼容导出。缺媒体应显式报告，不能用重新跑 AI 代替恢复人工成果。

## 7. 身份、状态与发布

本轮原卷沿用 `(paper_id, question_number)` 业务定位，内部稳定 item_id 不随展示 slug 改名。历史 Q001 用所属试卷限定别名；身份歧义进入处理列表，不自动合并。不同版本原卷显式区分；同源多卷保留各卷关联。无需先批量改旧目录。

content_hash 基于规范内容、来源证据及引用媒体 hash；排除绝对路径、时间戳与审批信息。规范化算法需版本化。同身份同内容可 noop；不同内容是新候选/修订，不能因 ID 已存在就跳过。

分别记录：

- 接收/编辑：尚未录入、待审草稿、已接收；
- 结构校验：未检查、通过、失败、因内容或校验器变化而失效；
- 内容复核：未复核、需修改、已批准、旧结论已失效，明确人工与模型身份；
- 发布：未发布、已发布、已撤回，固定到具体修订。

数据库保存草稿不等于正式发布。旧修订可已发布，新修订同时待审；新修订保存不改变旧发布指针。内容错误可显式撤回旧版本。沿用现有批准要求，不把模型审核或结构通过写为人工批准。

发布在数据库事务内检查目标修订、批准及预期旧发布版本，然后更新指针和记录。媒体先持久化到不可变位置并验证，事务再引用；失败留下的未引用资产可延迟清理。禁止先提交一个指向不存在媒体的修订。

旧消费者的导出失败不撤销已保存的人工作业，也不能显示导出已经更新。发布消费需要文件时，先生成完整版本化导出，再切换消费指针；分别显示数据库发布和导出就绪状态，重试按同一修订执行。程序崩溃恢复不得让消费者读到半套文件。

试卷进度从数据库逐题事实计算：预期、已接收、待人工调整、已批准、已发布及缺失题号。预期集合未知时显示 unknown，不以目录存在给 COMPLETE。全卷可用还要核对题序、分值和卷级来源/图归属；单题问题不阻塞已确认无关联的题继续处理。

## 8. 迁移与实施顺序

用户最新执行范围：跳过 C 存量迁移，A/B 后直接做 D 真实客户端 agent 录入和 E 真实 UI 验收。旧库保持原状，新录入使用独立管理数据库；下述迁移步骤仅作未来参考，不构成 D/E 前置条件。

### A. 先冻结接口和确认现有 UI 能力

梳理当前 draft、source、review、teacher/student 及图片接口的实际字段，确定单一题目编辑模型与适配映射。区分接收硬错误和可在 UI 修复的疑点。补当前 ID/逐题晋升回归，不能沿用旧验收结论。

### B. 做一题完整闭环

导入一题真实候选至数据库 → 现有 UI 展示 → 人工改文和改图 → 保存新修订 → 刷新及重启核对 → 复核 → 导出指定修订。先用固定候选验证，不必调用模型。此闭环未通过前，不扩大录入规模。

### C. 迁移现有数据，明确写入切换

对存量做只读盘点，导入已有内容、图片、批准与疑点；缺失历史标 unknown，不补造审核。核对题目数量、内容 hash、媒体引用和批准绑定。先复制演练并保留备份。

按明确题库范围短暂停止旧写入，处理增量后切换该范围的 UI 和导入入口到数据库；同一范围只能有一套写入后端。未迁移题库继续旧实现并显式标识。旧脚本对已迁移题库改为调用统一接口或拒绝直接写文件。

回退必须携带切换后的数据库新增修订和人工修改；不能恢复旧文件快照就宣称回退完成。未完成恢复验证前不删除旧证据和迁移备份。

### D. 接入逐题 AI 和局部修订

统一扫描聚合、任务派发、接收回执、有限修复与断点恢复。对 UI 发起的 AI 帮助按指定字段返回建议，验证不会覆盖人工作业。一题失败保留原因，其他题继续。

### E. 扩大验证并退役重复流

覆盖分卷答案、多图、缺答案和原卷瑕疵。真实模型试跑在明确预算下另行执行；对比请求、实际 usage、耗时、人工介入和内容错误。历史 107 请求/13M tokens/2.5 小时仅为一卷观测，不作为新系统保证。

闭环与恢复稳定后，旧编排只保留必要兼容与历史复现，SKILL 和运行入口统一更新；不再增加独立手填进度表或逐卷脚本。

## 9. 内容模型定稿：正文文本 + 结构化管理字段（2026-09-27 增补）

本节为内容模型的最终决定，覆盖前文与旧 draft/transcription 深结构冲突之处。

每个题目修订只保存**三块正文**：题目（stem）、答案（answer）、解答（solution）。正文是连贯的数学文本：小问、选项、推导顺序都在文本中表达，不再强制 choices[]、subquestions[]、solution_steps[]。示例：

```text
题目：已知二次函数 $y=x^2-2ax+3$。（1）当 $a=2$ 时，求函数的对称轴；
（2）若函数图像经过点 $P(1,0)$，求 $a$ 的值。

![题图](asset:fig-01)

解答：（1）当 $a=2$ 时，函数为 $y=x^2-4x+3$，所以对称轴为 $x=2$。
（2）将 $P(1,0)$ 代入，得 $0=1-2a+3$，解得 $a=2$。
```

仍保留少量结构化字段，因为这些事情需要程序准确处理：

- 身份与检索：item ID、所属试卷、题号、题型、分值。
- 图片：稳定引用（`asset:` 标记只出现在正文里）、原图、裁框等。Review UI 负责显示和调整。
- 来源与管理：来源页码/证据、修订版本、疑点、审核和发布状态。

Review UI 改题就是编辑一块文本；调整图片就是修改图片引用对应的资产或裁框。保存时程序将正文和图片关联一起保存为新修订。

校验随之减轻：接收层主要检查正文存在、图片引用有效、数据可保存和可呈现；不再要求 AI 为通过结构校验把一道题拆成复杂数据结构。数学是否正确、内容有没有漏录交给内容复核，不靠 JSON 字段齐全证明。

唯一保留的正文分隔是“题目”与“答案/解答”，避免学生端展示题目时混入答案。三块正文足以支撑该边界。后续备课需要详细解答图、教学步骤时，由 AI 从正文生成；它们是派生产物，不反过来增加题库录入负担。

### 插图与来源页的责任边界（2026-09-27 用户补充）

程序仅提供确定可直接复用的插图白名单，宁缺勿滥。AI 只能引用完整原图，并分别记录本题题干、解析所在的完整相关页；不能自行截图、裁图，也不能提交坐标让程序代裁。不确定或需要裁切的图全部留给人，候选记录待补图问题和来源页即可。

Review UI 直接展示相应原页，用户手动截图后粘贴/上传，或亲自在 UI 裁图；保存进入数据库的新修订。AI 的接收接口与工具限制必须落实上述边界，不能只写在提示词中。既有人工裁图、历史迁移和 UI 人工操作继续支持。

### 录入 agent 的执行位置（用户最新澄清）

录入和后续 AI 修订直接由 Codex/Claude Code 客户端中的现成 agent 完成。仓库提供材料准备、校验、接收、查询与 Review UI，不自建模型运行时、provider 适配器、工具调用循环或后台调度器；不要求 UI 自动启动模型。用户在客户端发起 AI 修订，agent 提交基于当前修订的建议，由现有接口和 UI 接收/比较，保护人工修改。本要求覆盖前文“程序组织模型任务”等可能被解释为开发模型执行服务的表述，具体实施见 C/D/E 接续计划 D2–D5。

## 10. 验收标准

| 场景 | 必须达到的结果 |
|---|---|
| AI 候选合法但图片待调 | 接收为待审，UI 可见原图和疑点，人能完成调整 |
| AI 候选结构不合法 | 返回具体题目/字段错误，不写入半题，不伪造通过 |
| 人在 UI 改文、裁图或换图 | 数据库形成新修订，刷新及服务重启后内容和图片一致 |
| 保存失败 | UI 不显示成功，保留未保存编辑，重试不重复创建 |
| AI 重交/网络丢回执 | 同提交同内容幂等；不同载荷同提交 ID 拒绝 |
| 人改完后 AI 再提交旧结果 | 不覆盖人工修改，出现版本冲突或独立建议 |
| 接受 AI 局部建议 | 只作用于确认范围，形成可追溯的新修订 |
| 修改已批准题目 | 旧批准留在旧修订，新修订重新核查 |
| 媒体落盘或事务阶段中断 | 无引用缺失媒体的已提交修订，可查询真实保存结果 |
| 导出失败 | 人工修改仍在数据库，导出状态准确，可重试同一修订 |
| 备份恢复 | 人工文字/图片修改、复核、发布及媒体引用一致 |
| 旧 Q001 跨卷重复 | 正确保留各卷身份，无误合并 |
| 一题阻塞或只抽查部分题 | 逐题状态准确，不宣称全卷已通过 |

## 11. 试卷目录与连续审核（2026-09-29 增补：老版查卷体验复刻）

背景：批量库已有三百余卷后，仅有"一个长下拉框"的目录不可用；用户要求以老版 Review UI（`.codex/skills/math-topic-question-bank/`，文件不改一行）的使用体验为基准，把「查卷—看题—修订—连续审核」接回数据库版。本轮范围与未恢复模块如下，验收通过只代表该范围，不代表老版全部功能复刻完成。

### 11.1 本轮恢复

- 试卷目录 `GET /api/papers`（`q/year/district/exam_type/grade` 筛选，响应含 facets 与每卷当前修订统计）；切卷只拉单卷目录 `GET /api/items?paper_id=...`，题目详情按需加载（缓存 + 邻题预取 + 请求竞态保护），前端不再依赖全库 bootstrap。
- 筛选栏（年级/年份/试卷类型/检索）+ 卷内题号筛选（本地）+ 筛选写入 URL 支持刷新恢复；筛选后当前卷仍在结果集时不打断浏览。
- 单题审核（A/R/按钮）成功后自动跳到卷内下一道待审题（环形扫描，排除本题；待审核/已过期算待审），失败留原题；跳转与结果有提示音与文字反馈。
- 全卷通过 `POST /api/papers/{paper_id}/review-all`（按钮与 `Shift+A`）：请求携带用户所见的 `{item_id, base_revision}` 清单；服务端核对试卷归属与清单覆盖；已批准当前修订跳过；阻断、版本冲突逐题返回——部分成功语义，失败留卷不跳转；全部通过后在当前筛选结果中跳下一份未完成卷。不自动发布、不解决疑点、不替用户保存未提交编辑。
- 进度统计基于当前修订：`pending/approved/rejected/stale` 互斥（旧修订批准、新修订未审核 → stale），`blocked`（未决阻断疑点或检查未过）与 `published_current` 为重叠维度；`expected_state=unknown` 时只显示"已入库题全部通过"，不声称原卷录入完整。

### 11.2 元信息确定性解析（不改 schema）

年份、区、考试类型没有独立字段：`scripts/question_bank/catalog.py` 从 paper_id 拼音 token（优先）与 title 中文关键词（兜底）确定性解析；解析不出返回 `null`（未知），不默认年级或考试类型；联合命题卷保留全部区（如 `2012-BAOSHAN-JIADING-ERMO` → 宝山·嘉定）。需要人工纠正元信息时，后续再以幂等迁移增加独立 `paper_metadata` 扩展表，不改题目修订、内容 hash 与旧提交包。

### 11.3 本轮未恢复（后续单独一轮，页面不放不可用按钮）

按小问的讲解/解答管理、录音（MediaRecorder）、ASR 转写、润色、自动生成与 teaching-tools blueprint 导出。它们是独立的教学内容生产功能：建议作为独立教学内容实体（关联 `item_id + source_revision`，自有版本与批准记录；音频为资产，转写稿/润色稿/讲解正文分开保存；原题修订后标记"来源已变化"并保留旧内容），不能把旧 `explanations.yaml` 直接接到新题目上，也不能塞进 `solution` 冒充原卷解析；模型生成入口另行确认，不借复刻新增模型运行时。

### 11.4 幂等与并发（review-all）

父 `operation_id` 同载荷重放回执、异载荷拒绝（409）；父操作行在整个逐题循环完成后写入，中途崩溃重试时已批准题按 skip 处理，子操作 ID 由父 ID 与 item_id 确定性派生，不重复写审核记录。审核写入测试使用独立测试库，不在批量成果库批量批准。

## 12. 教学内容（讲解/解答对）：老版 explanations 子系统复刻（2026-09-29 第二轮）

用户要求把老版剩余功能全部做齐：按小问管理多个讲解/解答对、录音→转写→润色、单对生成与一键补齐、列表缺项打标、批准后导出 teaching-tools blueprint。设计经 Codex 会话审查修正（见 artifacts/review-ui-teaching-notes/acceptance-task.md），实施如下：

### 12.1 数据模型（迁移 003）

- `teaching_notes`：一条记录 = 一个讲解/解答对（approach），软删除保留版本/审核/音频/导出溯源；`teaching_note_versions` 以 (note_id, version) 只追加，title/ordinal/小问归属也进版本（base_version 乐观并发）。
- `source_revision` 绑定创建/适配时的题目修订；普通编辑不刷新（不得洗掉"来源已变化"），显式 `readapt` 或基于当前题重新生成才建立新来源版本并需重新审批。小问从三块正文 stem 按老版（1）/(2)/① 规则派生，sqN 只作分组：同 ID 题干变化（stem_fingerprint 比对）也过期；不再匹配的 note 显示为额外小问，不删除不自动重绑。
- `teaching_note_reviews` 批准绑定具体版本；讲解与解答都非空才能批准；笔记批准不等于题目批准，全卷通过也不批准笔记。
- `ai_operations`：模型调用（转写/润色/生成）先登记再调用，调用不持写事务；结果落库复核版本与删除状态，冲突保留模型结果为未应用；同 ID 重放不重复付费调用；远端成功本地崩溃标 unknown，禁止静默重试。
- `assets.source_kind` 扩 `recording`（表重建迁移，数据无损、外键校验）；音频经 AssetStore 独立登记/读取（magic bytes、大小/时长上限、ffprobe 计时），图片接口继续拒绝音频；录音原件、ASR 转写稿、润色正文分开保存。
- `blueprint_batches/candidates`：本地不可变快照（exports/blueprints/<paper>/<hash>.candidates.json）+ 配置外部投递（QB_TEACHING_TOOLS_ROOT → teaching-tools authoring/tmp/reviewed-bank-import/），外部未配置明确 not_configured 不显示已交付；零候选也清理外部当前文件，不残留旧候选冒充当前结果。

### 12.2 模型调用边界（用户授权的有限例外）

恢复老版 UI 教学内容生产的固定 DashScope 调用（qwen3-asr-flash 转写、qwen-plus 润色/生成），移植为 `scripts/question_bank/explanations_ai.py`（模块级可 mock，适配三块正文上下文）。不扩展为 agent 运行时/通用调度/跨供应商回退；能力反馈区分服务器 ffmpeg、ASR、LLM 配置。

### 12.3 导出语义

正式 blueprint 要求：题目当前修订已批准 + 笔记当前版本已批准 + 来源不过期；不以 allow_draft 绕过。candidates 沿用真实消费者结构（taskId/engineKind/contentId/version/candidates + promptData/answerKey/metadata），assignments 指向现有 export_revision 产出的指定修订 teacher.assignment.yaml；answerKey.solutionSteps 为三块正文 solution 的兼容分步条目。已用真实 teaching-tools authoring/scenario_pipeline.py generate 验证消费。

## 13. Review UI 修订交互（2026-09-30）

- 桌面使用题号列表、题目正文、审阅侧栏三栏布局，正文和审阅分别滚动；窄屏顺序显示。
