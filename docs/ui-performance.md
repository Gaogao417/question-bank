# 题库交互性能指标与验收

目标是让用户尽快开始选卷、读题和审核。目录、正文、公式、图片分别计时，外部资源不能阻塞目录或正文。以下数字是首轮验收目标，尚不是线上实测结果。

## 交互目标

基准环境：桌面 Chromium，4 核 CPU、8 GB 内存，客户端 RTT 100 ms、下行 10 Mbps、上行 2 Mbps。分别测冷缓存、热缓存；登录耗时不计入已认证首屏。移动设备和更差网络单列，不能混入基准分位数。

| 交互 | 起止口径 | P50 | P95 | P99 |
| --- | --- | ---: | ---: | ---: |
| 首屏目录 | navigationStart 到试卷选择器可操作 | 600 ms | 1.2 s | 2 s |
| 首题可操作 | navigationStart 到正文及当前题操作区完成渲染 | 1 s | 2 s | 3 s |
| 切卷 | 用户选卷到新卷首个目标题可操作 | 400 ms | 800 ms | 1.5 s |
| 切题，未命中缓存 | 导航动作到目标正文可操作 | 200 ms | 500 ms | 1 s |
| 切题，命中缓存 | 同上，单独标记缓存命中 | 50 ms | 100 ms | 200 ms |
| 检索和筛选 | 最后一次输入到新目录可操作，含 300 ms 防抖 | 450 ms | 700 ms | 1.2 s |
| 保存和审核 | 点击到服务成功回执、状态已更新 | 300 ms | 800 ms | 1.5 s |
| 公式就绪 | 正文出现到当前可见公式排版完成 | 300 ms | 1 s | 2 s |
| 首张可见图片 | 进入题目到首张可见图片完成解码 | 500 ms | 1.5 s | 3 s |

按钮、加载提示应在操作后 100 ms 内反馈。超过 1 s 保留明确加载状态；公式超过 8 s 给出独立提示。失败不能显示成功，旧响应不能覆盖新选择；这些是正确性门槛，不能用更低耗时抵消。

服务端预算（不含公网 RTT）：试卷目录 P95 ≤ 200 ms，单卷题目目录 ≤ 200 ms，题目详情 ≤ 250 ms，保存／审核 ≤ 400 ms。交互错误率 < 0.5%，服务端 5xx < 0.1%；用户主动取消单独统计，不算错误。按交互和网络条件分别计算，不把后台轮询或预取混入切题指标。

## 规模与测量方法

使用专用 PostgreSQL 测试数据库和模拟存储，禁止向正式题库写压测题。覆盖 100、500、2000 份试卷，每份 25 题；每题保留 1、10、50 次历史修订，包含人工批准、自动批准、新修订未审、阻断疑点、过期讲义与空卷。

每组先预热 20 次，再至少采集 200 次有效交互；P99 验收至少 1000 次。并发用户分别为 1、5、20，报告样本量、P50／P95／P99、超时、错误率、取消数、响应字节和 SQL 次数。冷缓存至少单列 30 次，样本不足不宣称 P99 达标。数据库首次初始化和进程重启冷启动单独统计。

目录查询次数应不随题目数、讲义数增长：非空试卷目录为 3 次 SQL，空筛选仅 1 次；非空单卷题目目录为 4 次（空卷 2 次）。筛选只查询命中卷的状态，切卷只查询目标卷；不从数据库传输所有历史审核与检查记录。目录统计仍随命中题量增长，若 2000 卷场景不达标，下一步将统计下推到数据库聚合并对目录分页，依据 EXPLAIN ANALYZE 决定索引。

对比优化前后使用相同数据集、浏览器、网络和并发条件；保留响应及状态语义一致性断言。重点测试 CDN 挂起／失败、快速连续筛选、跨卷深链、旧请求晚到、保存后刷新状态和有未保存草稿时切卷。未部署或未完成真实数据库回归不能标记线上验收通过。

## 已有测量入口

浏览器控制台执行 `console.table(window.qbPerformance.summary())` 查看当前页面样本；`window.qbPerformance.samples()` 导出原始样本；`clear()` 清空。最多保留 500 条，不上传数据，不记录题目正文、ID 或凭证。500 条仅适合快速诊断，P99 正式验收需外部采集器累计至少 1000 次。

已埋点：`api-catalog`、`api-directory`（含 JSON 解码）、`catalog-ready`、`directory-ready`、`item-ready-cached`、`item-ready-network`、`first-item-ready`。API 样本区分 ok、error、canceled；交互 ready 样本仅记录完成事件，不能据此单独计算交互错误率。`api-other` 包含预取及后台调用，只用于粗略诊断。

当前 ready 以 DOM 更新结束为止，不等同于浏览器已绘制。`catalog-ready` 从筛选函数开始计时，不包含输入防抖；`item-ready` 可能包含放弃草稿确认时间。正式验收需用浏览器脚本从用户动作计时，排除人工确认等待，等待目标控件状态和下一次绘制，另外记录公式完成、图片 decode 和保存回执。不要直接将现有内部计时与全部交互目标作等价比较。

## 本轮改动与发布边界

- MathJax 在正文首次绘制后独立 async 加载；目录与正文不再等待它。公式就绪后补排版，丢弃已移除的节点并串行排版；失败提示不占用目录错误区域。
- 试卷目录先筛选元信息，再查询命中卷的当前状态，保留全量 facets。
- 单卷状态、正文／审核元信息、讲义分别批量读取；复用原有状态与讲义判定规则。
- 取消过期目录请求，保留响应令牌校验，避免旧请求重新启用正在加载的试卷选择器。
- 静态脚本与大于 1000 字节的接口响应支持 GZip，保留 Vary 与认证行为。

MathJax 已固定为 4.1.3，并将运行脚本、动态模块、CHTML 字体和许可证放入本地静态资源；wheel 包已核对包含嵌套字体与模块。修正了原配置对括号／方括号公式分隔符的重复转义。

2026-10-25 在独立临时 PostgreSQL 数据库中运行，232 项 Python 测试全部通过。专项浏览器回归通过：公式库人为延迟 5 秒时目录与正文可操作、本地字体和动态扩展无外部请求、快速筛选与切卷不被旧请求覆盖。所有临时数据库均已清理。

完整历史界面脚本尚未全部通过：存在已移除的保存按钮选择器、旧灯箱属性与旧审核提示等待条件。不能将专项回归表述为完整编辑／审核 E2E 全通过。部署验收采用上述专项回归与数据库回归，完整历史脚本维护仍待完成。

## 线上复测结果

2026-10-25 已重启 question-bank.service，状态 active/running；认证仍有效。相同本机 HTTP 入口各采集 5 次，单卷题目目录中位数从 647.63 ms 降到 17.80 ms，约快 36 倍。全量试卷目录中位数从 253.90 ms 到 267.36 ms，没有测得改善；运行期间有真实录入请求，不能视为受控负载对照。

线上只读浏览器验证没有页面错误或外部资源请求。单次冷首题可操作时间为 3827.5 ms，尚未达到 2 秒目标；此单样本不是 P95 验收。后续应区分数据库新连接等待、并发录入影响与客户端耗时，再按前述样本规模验收。完整原始样本与边界见 [复测记录](acceptance/2026-10-25-ui-performance/results.json)。
