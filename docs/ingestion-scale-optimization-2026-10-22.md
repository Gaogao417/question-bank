# Question Bank 大图与并发录入优化

本轮针对合计约 1 MiB、4 MiB 的图片资源和 1、4 个并发调用进行短时对比。4 MiB 档单并发平均录入耗时从 1.78 秒降到 0.67 秒；4 并发吞吐从 0.53 提升到 2.08 题每秒。资源读取、摘要校验、事务内复核和数据库写锁均保留。

## 实现变化

第一项是避免无用 PNG 编码。此前结构校验调用完整渲染流程，把图片解码、转换、裁剪、旋转，再编码为 PNG，随后丢弃结果。现在校验与预览共享解码和图像变换逻辑，校验在编码前结束；用户实际预览和导出仍生成 PNG。对大图，省掉的是重复压缩 CPU 与输出缓冲开销，未省略可解码性、摘要和裁框检查。

第二项是移除 submit_candidate 整个方法外层的进程互斥锁。该方法的候选包、资产登记集合和校验结果均为请求局部数据，连接由线程独立持有；允许各请求的资源准备和事务外校验重叠。最终修订、基线检查、回执重放和写入仍在 schema 级 advisory transaction lock 内执行，数据库唯一约束保留。其他写方法的互斥锁未改动，没有引入任务调度服务。

新并发回归以同一 service、相同 submission_id 同时提交，并在首个资产处理处设置 barrier，验证准备阶段确实重叠且最终只有一条修订、一条回执，一个新成功、一个重放。新图像回归禁止校验调用 PNG 编码，同时检查裁框越界仍拒绝，实际预览仍产生正确格式。

## 负载与结果

每个档位 8 次请求，共 32 次；每题 4 张 512×512 或 1024×1024 灰度噪声 PNG，合计分别为 1,052,223 和 4,204,433 字节。固定随机种子，优化前后相同字节。噪声图用于避免纯色图的过高压缩率，不代表真实试卷图像分布。

每档资源先上传，计时阶段重复复用相同 key，没有 PUT；连接也先初始化。采用单个共享 QuestionBankService，线程池模拟 1 或 4 个调用方，闭环发请求。测量包含请求排队、OSS 读回、图片处理和 RDS 写入，不含包生成或模型。它测量热资源录入，不测冷上传，也不是完整 HTTP/UI 压测。

| 每题资源总量 | 并发 | 平均耗时前后 | P95 前后 | 吞吐前后 |
| --- | ---: | --- | --- | --- |
| 约 1 MiB | 1 | 690 → 512 ms | 741 → 717 ms | 1.45 → 1.95 题/s |
| 约 1 MiB | 4 | 2247 → 1160 ms | 3453 → 1677 ms | 1.45 → 3.13 题/s |
| 约 4 MiB | 1 | 1778 → 666 ms | 1854 → 749 ms | 0.56 → 1.50 题/s |
| 约 4 MiB | 4 | 6225 → 1730 ms | 8061 → 2581 ms | 0.53 → 2.08 题/s |

所有档位均 8/8 accepted；每档均为 96 GET、32 HEAD、0 PUT，优化前后相同。P95 使用 nearest-rank；样本只有 8 次，因此 P95 等于该档最大值，尾延迟结论非常有限。1 MiB 单并发 P95 改善很小，不能据此声称所有大小都同比提速。

4 并发时事务锁获取平均耗时从约 3 ms 增到 274–346 ms：请求不再在 Python 方法锁外全程排队，而是在经过并行准备后等待提交锁。总体吞吐提高，但提交锁仍限制扩展性。没有继续削弱这层保护，也未将“锁等待变大”误解为整体性能倒退。

## 测试隔离与边界

每轮都创建独立 qb_scale 临时数据库，OSS 写入限定到随机 acceptance 前缀，均清理并核对成功；没有向正式 question_bank 数据库写入测试题。使用同一 RDS 实例和 bucket，因此会共享 CPU、I/O、网络和请求配额。保持最高 4 个客户端的短时负载；没有重启、部署或修改线上 8890 服务。

优化后测量期间专用数据库回归亦在运行；不是独占实例的可控实验。两轮没有模拟网络故障，不能以此承诺生产 SLA。每个请求校验最多 4 个 worker，多个请求可叠加，后续提高并发前需观测内存、OSS请求量和连接容量。独立媒体灾备、对象不可变策略和 GC 的原有验收边界不变。

## 证据
